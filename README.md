# ReachInbox — Full-stack Email Scheduler

A React + Tailwind CSS / TypeScript email scheduler built for the ReachInbox hiring assignment. The UI follows the supplied white/green mailbox references: a narrow sidebar, Scheduled/Sent views, a full-page composer and a send-later popover.

## Technology stack

| Layer | Technology |
| --- | --- |
| Frontend | React, TypeScript, Vite, Tailwind CSS, Tiptap |
| API | Node.js, Express, TypeScript |
| Database | PostgreSQL 16 |
| Queue and sessions | BullMQ, Redis 7 |
| Search | Elasticsearch 8 |
| Email | Nodemailer with Ethereal SMTP |
| Authentication | Google OAuth 2.0 with Redis-backed sessions |
| Notifications | Slack OAuth and incoming webhooks |
| Queue administration | Bull Board |

## Prerequisites

- Node.js 22 or newer and npm.
- Docker Desktop running with Linux containers and Docker Compose.
- A Google account and a Google OAuth web application.
- A Slack workspace where you can install an app, for Slack integration.
- Internet access for OAuth, Ethereal account creation and outbound SMTP on port 587.

PostgreSQL, Redis and Elasticsearch run locally in Docker; separate cloud accounts for these services are unnecessary.

## 1. Install and configure

Run commands from the project root, where `package.json` and `compose.yaml` are located.

```powershell
cd C:\VSCode\ReachInbox-Project
npm ci
npm run setup
```

`npm run setup` creates a root `.env` from `.env.example`, generating random session and encryption keys. If `.env` already exists, it leaves it unchanged.

Edit `.env` locally. Never commit it. Commit `.env.example` with placeholders only.

| `ENCRYPTION_KEY` | Exactly 64 hexadecimal characters; generated by setup |
| `GOOGLE_CLIENT_ID` | Google OAuth web client ID |
| `GOOGLE_CLIENT_SECRET` | Secret belonging to that Google OAuth client |
| `GOOGLE_CALLBACK_URL` | Browser origin followed by `/auth/google/callback` |
| `SLACK_CLIENT_ID` | Slack app Basic Information → Client ID |
| `SLACK_CLIENT_SECRET` | Slack app Basic Information → Client Secret |

### Google OAuth setup

1. Open [Google Cloud Console](https://console.cloud.google.com/) and create/select a project.
2. Configure the Google Auth Platform consent screen with app name and contact details. Add your demo accounts as test users when using testing mode.
3. Create an OAuth client with application type **Web application**.
4. Add the exact authorized redirect URI for the mode you will use:
   - Development: `http://localhost:5173/auth/google/callback`
   - Built local app: `http://localhost:3001/auth/google/callback`
   - Public demo: `https://YOUR-HOST/auth/google/callback`
5. Put its client ID and secret into the root `.env`.
6. Set `GOOGLE_CALLBACK_URL` to the registered URI and `APP_URL` to that browser origin.
7. Set `ADMIN_EMAILS` to your Google login email, then restart the API.

The app requests `openid email profile`; it does not require Gmail sending permissions. Google handles authentication; Ethereal handles email testing.

| --- | --- | --- |

## 5. Set up Ethereal Email

1. Sign in through Google.
2. Open **Senders & integrations**.
3. Enter a sender name and click **Add sender**.
4. The backend creates a fresh Ethereal account and stores its SMTP password encrypted in PostgreSQL.
5. Add a second sender to test independent rate limits. The app supports up to 10 senders per user.
6. Compose a message, choose a sender and schedule it.
7. After it becomes `sent`, open the message and click **View in Ethereal** to inspect the captured email.

No manual Ethereal signup, `SMTP_USER`, `SMTP_PASSWORD` or Ethereal API key is required by this implementation. SMTP credentials belong to each sender and are stored in the database, not the root `.env`.

The worker connects to `smtp.ethereal.email:587` with STARTTLS. Ethereal captures messages for inspection; it does **not** deliver them to recipients' real inboxes. A `sent` status means SMTP acceptance by Ethereal.

## 6. Set up Slack

1. Use a public HTTPS app origin as described in [HOSTING.md](docs/HOSTING.md).
2. Create an app at [Slack API](https://api.slack.com/apps) in a workspace you can manage.
3. Enable Incoming Webhooks and configure the `incoming-webhook` bot scope.
4. Register the exact HTTPS `SLACK_CALLBACK_URL` in OAuth & Permissions → Redirect URLs and save it.
5. Copy Client ID and Client Secret from Basic Information into `.env`; restart the API and worker.
6. Sign in with Google at the HTTPS app URL, then select **Connect Slack** inside the app.
7. Authorize the installation and choose a channel. The app encrypts and stores the returned webhook and access token.
8. Create a fresh sender, schedule four recipients with a limit of two/hour and a two-second delay. Two attempts should be allowed, the rest deferred, and a real alert should appear in the selected channel.

Use OAuth through this app instead of manually pasting a webhook. Slack token rotation is not implemented. Disconnect/reconnect is available in settings without rebuilding or restarting the application.

## Architecture

The browser submits a batch to Express. A PostgreSQL transaction stores the batch and recipient records. A dispatcher adds each recipient to BullMQ with a stable job ID and a delay calculated from the scheduled timestamp. The worker enforces the sender's shared allowance immediately before sending through Ethereal. PostgreSQL records the outcome; a separate indexing loop publishes changes to Elasticsearch. Slack notifications are durable database records processed independently of email delivery.

The database is authoritative. Redis is the scheduler/session/throttling store; Elasticsearch is a derived search index. All data reads are scoped to the logged-in user. SMTP passwords, Slack tokens and webhook URLs use AES-256-GCM encryption. **Keep `ENCRYPTION_KEY` and `SESSION_SECRET` stable across restarts.** Losing the encryption key makes stored credentials unreadable.

### Scheduling and restart behavior

- A batch commits before returning success. No in-memory timer is responsible for an email's due time.
- Pending dispatch rows survive API/worker restarts. Dispatcher row locks support multiple processes.
- If enqueue succeeds but the database update fails, the stable BullMQ job ID deduplicates the next enqueue attempt. Completed queue records are retained for this demo.
- A reconciliation loop repairs missing queue entries for scheduled/deferred database records. It does not resend terminal records.
- Future jobs retain their timestamps. Overdue jobs become eligible after recovery, subject to sender limits. Exact wall-clock delivery is not promised during downtime or backlog.
- Docker persists PostgreSQL, Redis and Elasticsearch in named volumes. Redis uses AOF with `appendfsync everysec`; catastrophic Redis loss may lose the newest second of budget/session data. This is not a zero-data-loss multi-region design.
- Background loops perform outbox transport, reconciliation, indexing and notifications. They are not cron schedulers; all email due times are BullMQ delayed jobs.

### Concurrency, delay and rate limiting

`MIN_DELAY_MS` defaults to 2,000; `MAX_EMAILS_PER_HOUR` defaults to 200; `WORKER_CONCURRENCY` defaults to 5. The composer can choose a stricter sender allowance. The current configuration must remain unchanged while that sender has pending messages, avoiding incompatible rules across overlapping batches.

The Redis Lua script reads Redis's clock, checks the fixed UTC hour, enforces minimum spacing and reserves one send attempt atomically. A shared sender lock ensures one SMTP operation at a time for that sender, while different senders can progress concurrently. Earlier pending messages take precedence. Rate-limited jobs return to delayed state with the next eligible time.

Budgets count **attempt reservations**, not only successful deliveries. Failed or interrupted sends conservatively consume allowance. This prevents retries from bypassing provider-style limits. At the reservation that reaches the limit, a unique sender/hour notification is persisted if Slack is connected. Slack failure does not stop email processing. Notification delivery retries use capped backoff; an uncertain HTTP response can cause an occasional duplicate alert.

### Duplicate prevention and SMTP ambiguity

Repeated API requests with the same idempotency key and payload return the existing batch. A different payload with that key returns 409. Each recipient is unique within a batch. Already sent/failed/uncertain records are never automatically resent.

Plain SMTP has no transactional exactly-once primitive shared with PostgreSQL. If SMTP accepts a message and the process crashes before recording success, the record becomes `uncertain` instead of blindly resending. Inspect Ethereal before scheduling a replacement. Explicit SMTP rejection is `failed`; ambiguous timeouts are `uncertain`. The deterministic Message-ID is useful for investigation but is not a provider deduplication guarantee.

### Search

The worker creates `reachinbox-emails`, indexes searchable text and status with an external document version, and records which version was indexed. Failed indexing retries without changing email outcomes. Results can lag updates by the indexing loop plus Elasticsearch refresh interval. Search failures are reported rather than silently replaced by SQL substring search.

### Security and scope

HTTP-only SameSite cookies, OAuth state checks, session regeneration, CSRF headers, tenant-scoped database/search queries, sanitized rich text, encrypted integration credentials and an admin-only queue dashboard are included. The local database/search ports bind only to loopback. Do not expose them publicly using this development Compose file.

The optional backend development login is disabled by default and unavailable in production. Google OAuth is the supported demo login. Password authentication, archive/delete actions and binary email attachments are outside the implemented scope; CSV/TXT files import recipients rather than becoming email attachments.

Unit tests cover lead parsing, server deduplication, input validation, batch size, planned ordering, stable job IDs and bounded retry delay. ## Troubleshooting

| Symptom | Action |
| --- | --- |
| Docker Linux engine pipe missing | Start Docker Desktop and wait for the Linux engine to be ready |
| Page unavailable after build | Start the API and worker; `build` only produces files |
| Session store unavailable | Check Redis health and `REDIS_URL`, then restart the API |
| Origin not allowed | Browser origin must equal `APP_URL`; restart the API after correcting it |
| Google redirect mismatch | Match the exact callback URI in Google and `.env` |
| Slack callback says sign in | Start Google and Slack OAuth on the same HTTPS origin in the same browser |
| Emails stay scheduled | Check the worker process and Bull Board; inspect deferral reasons |
| Search unavailable | Check Elasticsearch and worker logs; rebuild after source changes and restart after env changes |
| Elasticsearch yellow on one node | An unallocated replica can cause yellow; inspect errors rather than deleting the index |
| Queue monitor forbidden | Add the signed-in email to `ADMIN_EMAILS` and restart API |
| Vite chunk warning | A successful build with a bundle-size warning is not a startup failure |
